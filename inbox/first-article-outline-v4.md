## A. 骨架审核：保留结构，调整论述重心

这套骨架没有根本问题，适合面向听说过 AI 工具、想了解个人智能体的读者，写成“产品解释 + 上手指南 + 个人实践”。不必为了吸引点击，把整篇改成付款教程。

| 原有要点 | 问题 | 建议处理 |
| --- | --- | --- |
| 什么是 Grok Bot：personal agent | 英文标签不能解释读者会怎样使用它 | 讲清长期角色、云端工作环境、交代任务与检查交付 |
| 除了 AI，还有高配云电脑 | 容易把规格作为核心价值；未查到统一 CPU、内存、磁盘配置承诺 | 改为“有可持续使用的云端工作环境”；配置截图仅代表自己的实例 |
| 所有资料和命令操作在云端 | 表述过于绝对 | 默认云端执行，同时存在经授权的本地执行能力 |
| 每个 Bot 就是一个员工 | 比喻好懂，但要补组织方式和边界 | 讲角色与记忆分别保留；同账号共享电脑与登录状态 |
| 群聊、创建导入、应用、定时任务 | 不同层次的功能堆在一起 | 按“分工 → 使用工具 → 固化方法 → 定时执行”分开解释 |
| 底层模型切换 | 当前官方资料不支持用户切换模型 | 改成“系统按任务选择模型”，归入需要知道的限制 |
| 怎么用：注册、订阅、安装 | 到安装就结束，读者还没有完成一次使用 | 补“创建角色 → 派任务 → 接入工具 → 检查结果” |
| 案例：代理、X 运营、日报 | 案例性质和读者熟悉程度不同 | 日报讲透；X 运营补应用跨度；代理作为云电脑扩展场景 |
| 踩坑：额度不够 | 缺消耗机制和影响，容易成为一句抱怨 | 补周额度、按需计费、任务频率、网站障碍、云电脑维护 |
| 附：更新清单 | 容易冲淡主线，也容易过时 | 只选影响使用方式的变化，标日期和版本 |

建议暂定题目：《Grok Bot 是什么，怎么用？我的云端 AI 助手上手与实践》。如果口述后案例足够扎实，再调整为更有个人经历感的标题。

核心问题：读者能否看懂它如何替自己处理工作，并判断值不值得尝试？

## B. 建议的文章一、二级大纲

### 开头：用一个结果，让读者知道这篇文章会解决什么

用约一段话展示一个实际产物，优先选择容易看懂的日报或研究结果。只说任务、交付和自己的第一感受，完整过程留到第四章。

可用开场方向：“最近我开始尝试把一些固定工作交给 Grok Bot，例如……这篇把它的工作方式、上手过程和我的实际经验讲清楚。”实际工作名称、效果和使用天数由作者填写。

### 1. 什么是 Grok Bot：一个有角色、有工作环境的 AI 助手

#### 1.1 一句话解释它是什么

Grok Bot 提供可以长期保留的 AI 工作伙伴。用户通过消息交代目标、背景和工具访问，它在云电脑上处理跨网站、跨应用的多步任务，并在对话中汇报进度、交付结果或请求必要确认。[官方产品概述](https://cursor.com/docs/grok-bot)

介绍时先说“你给它一件事，它使用工具去做，最后你检查交付”，再引入 personal agent / 个人智能体这个名字。

#### 1.2 讲清三个层次：模型、Bot、云电脑

用功能关系帮助读者理解：模型提供判断与生成能力；Bot 承担持续的工作角色；云电脑提供浏览器、文件系统和终端等执行环境。这是基于官方工作机制整理的解释框架。

官方明确：同一账号下的多个 Bot 共享一台持久云电脑，各有工作屏幕。不能写成“每建一个 Bot，就得到一台全新的独立服务器”。[官方产品概述](https://cursor.com/docs/grok-bot)

#### 1.3 用一个连续例子解释工作过程

建议用“整理一份 AI 日报”作教学例子：作者给出信息范围和格式 → Bot 收集资料、处理文件 → 交付带来源的日报 → 作者核对、纠正 → 下次复用要求。

这个例子的作用是解释产品，不提前宣称作者已经自动发表日报，也不把生成草稿和正式发布混为一谈。

本章过渡：“理解了它怎么工作，接下来就能看出，哪些能力对我有用。”

### 2. 为什么值得尝试：它怎样进入日常工作

#### 2.1 云电脑让任务有一个持续的工作现场

浏览器、文件和登录状态可以在任务之间保留，方便继续工作。后台任务运行在云端，关闭本地应用或电脑不会直接停止云端任务。[官方 FAQ](https://cursor.com/help/grok-bot/faqs)

讲述重点：用文件夹、浏览器和任务画面展示“工作现场”；如果要展示机器配置，标设备实例、套餐和查看日期，不把自己的配置推广成所有人的固定待遇。

#### 2.2 多设备跟进同一份工作

官方移动帮助页确认支持 iOS 与 Android；用同一账号可跟进同一组 Bot 和云电脑，已有权益不必在手机上重复购买。云电脑更新、恢复和重置仍需桌面端。[官方移动使用说明](https://cursor.com/help/grok-bot/mobile)

讲述重点：多设备的价值是换设备后继续派活、查看结果或处理需要自己的步骤。若未在 Android 上实测，只介绍官方支持，不说自己测过。

#### 2.3 按职责分 Bot，再让它们协作

Bot 可以分别保留角色、对话和工作记忆；可以群聊和相互交接。共享电脑方便复用文件和登录，但角色划分不会形成账号权限隔离。[官方工作说明](https://cursor.com/docs/grok-bot/work)

讲述重点：用“资料搜集、成稿、检查”三个职责说明为什么分工；不用 Bot 数量证明效率。作者可补自己的 Bot 列表、实际分工，以及是否发生过重复工作。

#### 2.4 应用接入，让结果落到实际工具里

插件通过用户授权的服务账号执行操作，只能使用该账号已有权限。安装成功不等于授权完成。Gmail、Notion、Slack 等有对应接入方式；没有合适插件的网站，则可能需要在云电脑浏览器中登录和操作。[官方插件说明](https://cursor.com/help/grok-bot/connect-plugins)、[官方上手文档](https://cursor.com/docs/grok-bot/get-started)

讲述重点：围绕一个案例介绍需要接入的应用，避免罗列全部插件。区分应用已连接、实际读取成功和写入成功。

#### 2.5 从一次性任务，变成可复用方法和例行工作

Skill 保存“怎么做”的方法，Routine 决定“什么时候做”。官方建议先完成一次任务、改到可靠，再保存方法并自动执行。Routine 可按时间或受支持的事件触发，时区和执行结果可以查看。[官方工作说明](https://cursor.com/docs/grok-bot/work)、[官方 Routine 帮助](https://cursor.com/help/grok-bot/routines)

讲述重点：仍沿用日报例子，从手动一次、固定格式讲到每天定时；没有实际连续运行记录时，表述为可配置能力。

#### 2.6 Bot 邮箱：给工作流程增加一个入口

官方已提供 `mail.grokbot.com` 地址功能，可接收、读取、搜索和发送邮件。可以让 Bot 申请地址，经确认后创建。收到邮件本身不会自动唤醒 Bot，需要设置相应 Routine；团队账号还需要管理员启用。[官方 Bot 邮箱说明](https://cursor.com/help/grok-bot/agent-email)

讲述重点：用“接收订阅资料，再整理摘要”解释它的用途；区分 Bot 自有邮箱与接入个人 Gmail。没有实际使用过时，放在更新附录简讲。

本章过渡：“这些能力是否适合自己，最好通过一个小任务验证。下面讲如何开始。”

### 3. 怎么开始：从账号到第一个可检查的结果

#### 3.1 先看已有权益，选一条上手路径

付费 Cursor 个人套餐和 self-serve Teams 包含访问权益；符合条件的 SuperGrok 或 X Premium+ 可以通过账号关联获得权益。试用按工作消耗额度，并有 7 天窗口，不能理解成 7 天无限用量。[官方 Grok Bot 套餐说明](https://cursor.com/help/grok-bot/plans)

建议正文以作者实际使用的 Cursor 路径为主，其他路径只给分支入口。个人 SuperGrok / X 的关联步骤见官方页面，不要把“关联”描述为购买 Cursor 套餐；关联不可随意解除或迁移。[官方账号关联说明](https://cursor.com/help/grok-bot/supergrok)

#### 3.2 订阅与付款：讲清价格，再讲本人走过的步骤

官方当前列出的 Cursor 个人月付标价：Pro 20 美元、Pro+ 60 美元、Ultra 200 美元。美元标价不是作者支付宝实付金额。[官方套餐价格](https://cursor.com/help/account-and-billing/pricing)

按作者实操补：入口、套餐、月付或年付、币种、支付方式、实付金额、订阅成功页。

支付宝支持有官方论坛工作人员回复，但 2026-05-29 的回复同时明确：是否显示受地区、币种和升级套餐影响。此次没有进入作者结账页，因此不能把“选 CNY 一定出现支付宝”“清缓存必能解决”写成通用规则。[官方论坛付款说明](https://forum.cursor.com/t/i-wish-cursor-could-support-alipay-payment/100728)

#### 3.3 下载、登录和基本设置

桌面端支持 macOS、Windows、Linux；官方提供 Cursor dashboard 的 Grok Bot 下载入口。常规个人路径使用 Cursor 账号登录；旧 Privacy Mode（Legacy）账号需要按提示切换隐私模式。[官方上手文档](https://cursor.com/docs/grok-bot/get-started)

按作者当前界面补安装、登录成功、套餐确认与时区设置截图。账号排障要区分两项：Privacy Mode（Legacy）与旧 request-based 计费套餐。官方论坛 2026-08-28 的回复确认，旧 request-based 用户需转为 usage-based 才能使用 Grok Bot；团队文档也列明旧计费与旧隐私模式会阻止启用。迁移对本人账单与原有权益的影响应核对当前 Dashboard，不据此宣称所有老用户都必须迁移，也不把迁移当作无成本操作。[官方论坛回复](https://forum.cursor.com/t/cursor-says-grok-bot-is-included-with-pro-now-do-you-actually-have-access-yet/169808/10)、[官方团队说明](https://cursor.com/docs/grok-bot/teams)

#### 3.4 创建第一个 Bot，给它一个明确的工作角色

官方流程会初始化首个 Bot；之后可从 New 创建其他 Bot，并设置名称、职责标签和描述。[官方 Onboarding](https://cursor.com/help/grok-bot/onboarding)

建议角色说明采用“负责什么、用什么资料、交付什么、什么时候停下来找我”四项。

写作示例，非本人已验证配置：“你负责整理 AI 产品动态。优先查原始公告，保留来源和日期；用中文写简洁摘要。资料不足就注明，不替我对外发布。”

#### 3.5 派第一次任务，接入必要工具，检查交付

把任务写成“目标 + 时间范围/输入 + 输出格式 + 检查标准 + 操作范围”。只接入这次任务需要的应用；网站验证码或登录等步骤可能需要用户接手。[官方上手文档](https://cursor.com/docs/grok-bot/get-started)

建议首个任务：围绕一个明确的 AI 产品，整理指定时间范围内 5 条有原始链接的动态，逐条写日期、发生了什么、为什么相关，保存成一份稿件。这个提示词是写作建议，需作者实际跑通后才能作为复现教程。

结果验收至少看：链接能打开、日期符合范围、内容有原文支持、文件可以取得。完成后再讨论是否保存 Skill 和建立 Routine。

本章过渡：“上手只是第一步，下面用我的实际工作说明它到底能做到哪一步。”

### 4. 我的使用案例：信息整理、内容运营与云电脑扩展

#### 4.1 日报：从收集信息到交付成稿

作为主案例的理由：读者容易理解，可以展示来源、筛选、成稿、检查和后续自动化的完整流程。

案例展开顺序：原本怎么做 → 交给 Bot 的部分 → 原始指令 → 资料与工具 → 第一次结果 → 作者纠正 → 最终产物 → 后续是否定时运行。

建议拆清工作环节：收集、去重、筛选、写摘要、排版、审核、发布。作者分别标明哪些已经跑通；官方支持资料处理和 Routine，不等于作者已经完成正式发表。官方案例也把交付和需要确认的外部动作分开。[官方用例](https://cursor.com/docs/grok-bot/use-cases)

作者待补：真实日报、信息来源、被纠正的问题、人工用时、额度记录、实际运行次数。没有连续记录就不说“稳定每天自动跑”。

#### 4.2 X 运营：把笼统名称拆成明确任务

建议按作者实做选择环节：关键词搜集、原帖分析、选题判断、稿件准备、已发布数据复盘。说清哪一环节由 Bot 完成，不用“运营账号”概括全部工作。

官方 X 文档说明，X 插件可用于搜索帖子、读时间线、查看提及、趋势和书签；在支持地区还可以通过 `@bot` 把帖子交给个人 Bot。`@bot` 的确认回复仅代表请求转交，结果仍在应用里，不等于工作已经完成。[官方 X 接入说明](https://docs.x.ai/grok-bot/tag-on-x)

作者待补：实际使用插件还是浏览器、用了哪些指标、得到什么选题或稿件、是否真的发出、有什么效果。“读 X”与“代替我发帖”要分别描述。

#### 4.3 云电脑扩展：把它作为代理出口

作者已说明，这只是独立云端工作环境的一个扩展场景。保留在案例章，篇幅短于主案例。

先用一句话画清本人的链路：“我的设备 → 实际采用的连接方式 → Grok Bot 云电脑 → 目标服务”。然后补采用什么软件、怎样连接、能处理什么任务、实测结果和中断条件。

特别区分官方 `Route traffic through this computer`：其方向是“Bot 云电脑 → 本地电脑网络 → 目标服务”，与作者“把云电脑作为代理出口”的方向不同。不能把此开关当作作者方案的操作方法。[官方设置说明](https://cursor.com/docs/grok-bot/settings)

官方默认网络出口为客户共享 IP 范围，没有专属客户出口 IP。此次未查到把 Grok Bot 当通用代理服务的官方保证；作者方案按个人配置案例写，不推定所有账号都可稳定复现。[官方私有网络说明](https://cursor.com/docs/grok-bot/private-networks)

作者待补：已配置并实际跑通，还是仍在尝试；云电脑重建后是否需要重新配置。也可以在这一小节补一个本人实际做过的脚本或文件处理场景，帮助读者理解云电脑的更广泛用途。

本章过渡：“这些案例说明它能帮到我，但使用成本和限制也决定了能交给它多少工作。”

### 5. 踩坑与判断：什么会影响持续使用

#### 5.1 额度：讲清为什么消耗快，什么时候会产生额外费用

Grok Bot 的包含用量按周刷新；消耗与任务中的执行步骤和 tokens 有关，不按用户发了几条消息计。用完后，若开启 On-demand，会继续产生按需费用；月度支出限额也不是正在运行任务的即时硬停止线。[官方 Grok Bot 套餐说明](https://cursor.com/help/grok-bot/plans)

高频 Routine 会增加消耗。官方建议先降低不必要的运行频率、收窄触发条件。[官方 Routine 帮助](https://cursor.com/help/grok-bot/routines)

作者补充“额度不够”的实证：什么套餐、哪些任务、几次运行、用量前后变化、是否影响交付。不能拿 Cursor 编辑器的月额度或倍率直接推算 Grok Bot 的周额度。

#### 5.2 网络和网站登录：本地能连接，不等于每个任务都能完成

网站可能阻挡云端访问、要求验证码或重新登录；云端工具使用与本人电脑访问是不同路径。[官方 FAQ](https://cursor.com/help/grok-bot/faqs)

建议按“本地下载与登录 / 云电脑访问目标网站 / 插件实际调用 / 最终结果”四项记录。国内可用性按作者测试日期、网络和开关状态写。关闭代理截图只说明测试条件，结果还要用任务记录支撑。

#### 5.3 云电脑持久化与维护：更新前理解会保留什么

官方区分软件更新和电脑重建。电脑重建、Recover 或 Reset 可能移除已安装应用与软件包；无法保存时，很近的改动也可能丢失。[官方云电脑恢复说明](https://cursor.com/help/grok-bot/computer-recovery)

与代理、脚本场景关联：本人自装工具是否要重装？文件和登录是否保留？正文只讲影响案例的部分，详细故障步骤可放附录。

#### 5.4 模型、权限和结果：有哪些需要明确的边界

当前官方明确，模型按任务由系统选择，可能使用 xAI 或第三方提供商；用户看不到具体请求模型，也不能手动指定、切换或屏蔽某个模型。因此删除“底层模型切换”，也不要保证某个请求一定由 Opus 执行。[官方模型说明](https://cursor.com/help/grok-bot/models)

默认云端执行之外，授权后还能操作本地文件和命令。共享云电脑里的文件与登录并不按 Bot 隔离；角色命名不会创造权限隔离。[官方安全说明](https://cursor.com/docs/grok-bot/security)

讲述重点：用一次自己的返工或检查说明为什么仍需要验收。不要把“可交代工作”讲成每次都正确、无限运行或无人介入。

#### 5.5 我的使用判断：哪些工作值得继续交给它

建议按自己案例归纳：什么任务可清晰验收、需要重复处理、已有工具访问；什么任务需要频繁判断、容易被网站阻挡、成本与收益不匹配。

给读者一个从小任务开始的判断方法：选一件自己熟悉、结果能检查的事，记录人工介入和消耗，再决定扩大使用。正式结论依据作者经历，调研不能替作者决定“值不值”。

本章收尾：讲自己接下来会继续交给它什么，留下一个明确待观察问题。正文的判断在这里结束，附录用于查询。

## C. 整篇文章的逻辑脉络

主线：**看到结果 → 理解工作机制 → 理解对自己的价值 → 完成第一次使用 → 看真实案例 → 评估成本与限制 → 得到个人判断。**

章节职责要分开：

- 第一章回答“它怎样工作”，不用展开全部按钮。
- 第二章回答“这些能力为什么有用”，每项能力接一个用途。
- 第三章回答“我怎样开始”，操作直到第一次交付和验收。
- 第四章回答“在我这里实际做到了什么”，保留失败、返工和介入。
- 第五章回答“持续用会遇到什么，值不值得”，结合案例而不是另列空泛缺点。
- 附录承担变化快、需要查阅的信息，不继续发展正文论点。

用日报作贯穿例子，但各章讲不同层次：第一章讲任务机制；第二章讲工具、分工和复用价值；第三章讲首次操作；第四章讲本人完整经历；第五章讲成本与可靠性。避免每章都重讲一次日报全过程。

篇幅建议：开头与定义约 15%，价值约 20%，上手约 20%，案例约 30%，踩坑与判断约 15%；附录另算。比例仅供口述与编辑参考。
